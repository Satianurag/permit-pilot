# Permit Pilot — End-to-End Audit

**Date:** 2026-08-26
**Target:** https://permit-pilot-538666547847.us-central1.run.app (live Cloud Run deployment) + local codebase at `/Users/Apple/Documents/permit-pilot`
**Method:** Real browser automation (Playwright/Chromium) driving the deployed UI as clerk `maria`, plus authenticated and unauthenticated API probing, axe-core accessibility scans, mobile viewport testing, and simulated failure injection. Code was read only to explain observed behavior, never as a substitute for it.

**What was actually exercised:** login (valid/invalid/empty/expired token), task inbox + all 3 filters, permit search + debounce + status filter + empty state, agent registry drawer, all 5 case tabs on 4 different cases, all 7 department drawers, full intake with PLUTO lookup + PII packet + file upload + validation, Vertex briefing (x4), distribution refresh, claim create + respond lifecycle, approve-with-override to terminal state, workflow interrupt/resume, GCP Cloud Workflows trigger, agent gateway invoke (3 signature variants), back/forward/reload, deep links, 404 routes, bogus IDs, and injected 500/502/network-abort failures on the bundle, orchestrate, decision, and refresh endpoints.

---

## 1. Executive summary

Permit Pilot is a genuinely well-built shell around a genuinely real data integration. The Socrata/NYC Open Data work is not faked — I watched seven departments query eleven real datasets and return real violation counts, and the intake address lookup correctly resolved `761 MACON STREET, Brooklyn` to BBL `3014930048` / BIN `3040031` with the real PLUTO owner record. Intake validation, search, claims state machine, and the audit log are all wired and persistent.

But the product has **five defects that are individually demo-fatal**, and they are all in the first ninety seconds of the experience:

1. **The landing page is permanently empty.** "My Tasks" shows *No tasks in this view* for every filter, forever, while three real cases with open tasks sit in Permit search.
2. **The confirmation dialog renders in the top-left corner of the screen**, overlapping the header — on the approve/reject action, the most important interaction in the app.
3. **"Refresh from NYC Open Data" is a silent no-op** on every case created through the app, and it writes an audit entry falsely claiming a live data pull.
4. **Opening any case file takes 12–22 seconds.** Approving a case took 60+ seconds end to end.
5. **The SSN was not redacted.** I submitted `SSN 123-45-6789` into the intake packet and it is stored and displayed in plaintext, on a screen whose own placeholder text promises "SSN, email, and phone will be redacted automatically."

Separately, the three features the README nominates as the differentiators — the cite-or-reject Critic, the crash/resume durable workflow, and the signed-agent gateway — are all **unreachable or inert in the running product**. Not weak: unreachable. Details in §3.

There is also one real security hole: `POST /api/cases/{id}/workflow/resume` is completely unauthenticated on a public service, leaks case data, and mutates state.

## 2. What is genuinely strong

Stating this plainly so the criticism below is calibrated, not reflexive.

- **The NYC Open Data integration is real and specific.** Seven departments, eleven datasets, keyed on BBL/BIN. Evidence rows in each department drawer cite the actual Socrata dataset ID and value (`3h2n-5cm9 · active_violation_count: 0`, `skr7-cxt3 · open_dep_ecb_count: 43`). This is the strongest thing in the project and it is verifiably not mocked.
- **Intake form design is above hackathon average.** Focus lands on the first field, PLUTO lookup auto-fills BBL/BIN/borough/owner, single matches auto-apply with a toast, borough locks and explains itself ("Filled from BBL borough digit"), BBL/BIN are digit-masked and length-validated with specific messages, non-PDF uploads are rejected client-side, and the submit button reports state ("Running distribution…").
- **The claims state machine actually works.** Create claim → case moves to `Awaiting Applicant`; record response → `Awaiting Clerk` + a new task. Persisted, reflected in the badge, survives reload.
- **The audit log is real, append-only, and attributes actor + timestamp** on every event including system/department actors.
- **Trace spans are real** for cases created through intake: seven per-department spans with genuine durations (zoning 536ms, building 826ms, critic 48ms) plus Vertex briefing spans at 11040ms/4367ms.
- **The Vertex briefing is a real LLM call with a grounded prompt** and it produces accurate, non-generic output that correctly cites the actual failing department and violation count.
- **Session handling is correct.** Invalid/expired token produces a clean redirect to `/login?expired=1` with an honest message and a saved return path.
- **Honesty in places.** `reviewClock.ts` labels the 5-day window "internal target — not a statutory NYC DOB SLA." The request-changes dialog admits "It does not notify the applicant automatically." The README has an explicit "Honest scope notes" section. This posture is a real asset — the problem is that it is applied inconsistently (see GAP-08).

#### GAP-01 · "My Tasks" is permanently empty for the seeded demo cases

**What is wrong.** The task inbox shows the empty state *"No tasks in this view"* under **all three** filters (Open / Completed / All), on a system that has three open tasks.

**Where.** `/tasks` — the post-login landing page and the app's primary daily surface. Confirmed in browser and by API:

```
GET /api/tasks?status=open&mine=true   → []          ← what the UI requests
GET /api/tasks?status=open             → 3 tasks     ← what actually exists
```

**Root cause.** Two halves that only break in combination:

```234:235:web/src/lib/api.ts
  listTasks: (status = "open", mine = true) =>
    get<Task[]>(`/tasks?status=${encodeURIComponent(status)}${mine ? "&mine=true" : ""}`),
```

`TasksPage` calls `api.listTasks(filter)` and never passes `mine`, so it always requests `mine=true`, which the API resolves to `assignee == "maria"`. But the seeder creates tasks with **no assignee**:

```71:75:packages/permit_pilot_core/permit_pilot_core/seeds.py
            store.create_task(
                case.id,
                title=f"Review distribution — BIN {case.bin or case.bbl}",
                task_type="distribution_review",
            )
```

Compare `cases.py:127-132`, which *does* pass `assignee=current_user.username`. So tasks created live in the app appear; the three seeded reference cases never do.

**Why it matters.** This is the first screen after login. A judge, a new employee, or anyone opening the deployed URL sees an empty product. The entire premise — "task inbox + case file" — reads as unimplemented. The three real cases are only reachable by knowing to click "Permit search."

**Ideal behavior.** Landing on `/tasks` shows the three open reviews sorted by review clock.

**Fix.** Either (a) assign seeded tasks to the bootstrap clerk in `seeds.py`, **or better** (b) make the inbox show unassigned work too, which is what a real permit queue does. Change `listTasks` to default `mine = false`, and add an explicit "Assigned to me / Unassigned / All" segmented control plus a **Claim task** action. That converts a bug fix into the missing multi-clerk workflow noted in GAP-14.

**Perspective:** E, C, P — all three, maximum severity on each.

#### GAP-02 · Confirmation dialogs render in the top-left corner, overlapping the header

**What is wrong.** Every `<dialog>` renders pinned at viewport `(0, 0)` instead of centered. Measured on a 1440×900 desktop viewport:

```
ConfirmDialog box = {x: 0, y: 0, width: 512, height: 188}
x_center = 256  (should be ~720)
```

The dialog visually covers the navy app header and the top-left of the page. Screenshot: `/tmp/pp-audit/shots/70-dialog-centering.png`.

**Where.** `web/src/index.css` `.pp-dialog`, affecting `ConfirmDialog` (approve dossier, request changes) and `IntakeModal`.

**Root cause.** Tailwind v4's preflight resets `margin: 0` on all elements, which overrides the browser's UA stylesheet `dialog:modal { margin: auto }`. `.pp-dialog` sets `width` but never restores the margin:

```48:55:web/src/index.css
.pp-dialog {
  width: min(32rem, calc(100% - 2rem));
  border: 1px solid var(--color-pp-border);
  border-radius: 0.5rem;
  padding: 1.5rem;
  background: #fff;
  color: inherit;
}
```

**Why it matters.** This is the most visible visual defect in the product and it fires on the approve/reject confirmation — the exact moment a judge is watching most closely. It reads as "unfinished," and it undermines every other polished detail in the app. The drawer variant is unaffected because `.pp-dialog-drawer` explicitly sets `margin: 0 0 0 auto`.

**Ideal behavior.** Centered modal with the backdrop behind it.

**Fix.** One line: add `margin: auto;` to `.pp-dialog`. Verify the drawer override still wins (it declares margin after, or scope it with `.pp-dialog:not(.pp-dialog-drawer)`).

**Perspective:** C, P (and E — it looks broken).

#### GAP-03 · "Refresh from NYC Open Data" is a silent no-op, and writes a false audit entry

**What is wrong.** On any case whose workflow steps are all `completed` — which is every case created through intake — clicking **Refresh from NYC Open Data** does nothing at all, gives no feedback, and appends an audit event claiming *"Live NYC Open Data pull (department workflow)."*

**Where.** Distribution tab. Measured `POST /api/cases/{id}/distribution/refresh` → **0.44s**, which cannot contain seven Socrata round trips (the real intake distribution took ~6s for the same seven).

**Root cause.** The route delegates to `WorkflowRunner.run_all`:

```161:168:services/api/permit_pilot_api/routes/cases.py
    runner = WorkflowRunner(store, engine)
    await runner.run_all(case.id, bbl=case.bbl, bin_=case.bin, work_type=case.work_type)
    store.append_audit(
        case_id,
        actor=clerk_actor(current_user),
        action="distribution_refreshed",
        detail="Live NYC Open Data pull (department workflow)",
    )
```

and `run_next` skips any step already terminal:

```84:86:packages/permit_pilot_core/permit_pilot_core/workflow/runner.py
        for step in steps:
            if step.status in {StepStatus.COMPLETED, StepStatus.FAILED}:
                continue
```

With all seven steps `completed`, `run_next` returns `None` immediately, `run_all` exits, and stale distribution rows are returned unchanged. The audit entry is written unconditionally either way.

Worse, this is **inconsistent**: the two seeded cases have *zero* workflow steps (the seeder calls `engine.run_all` + `save_distribution` and never creates steps), so `get_steps` initializes seven pending steps and refresh genuinely re-queries there. So the same button does real work on seeded cases and nothing on real cases.

**Why it matters.** Three compounding failures. The clerk believes they refreshed live data and did not. There is no success toast and no "last updated" timestamp anywhere in the distribution table, so **nothing in the UI can distinguish a successful refresh from a no-op** — this is precisely the "employee questions whether the system actually completed an action" scenario. And the audit trail, the compliance artifact, now contains a false statement about a data pull that never happened.

**Ideal behavior.** Refresh re-queries all departments, shows per-department progress, writes a truthful audit entry, and stamps a visible "Data as of <time>" on the table.

**Fix.** Add a `force: bool = False` parameter to `run_all`/`run_next` that resets terminal steps to `PENDING` before running, and have the refresh route pass `force=True`. Only append the audit event if steps actually ran, and include the count. Add an `updated_at` column to the distribution table and a success toast.

**Perspective:** E, C, P.

#### GAP-04 · The intake packet SSN was not redacted in production

**What is wrong.** I submitted this packet text through the intake form:

```
Applicant: John Smith, SSN 123-45-6789, email john.smith@example.com,
phone 212-555-0134. Architect: Maria Lopez, cell (917) 555-9876.
```

The stored and displayed result on the Documents tab:

```
Applicant: [PERSON_NAME], SSN 123-45-6789, email [PERSON_NAME][EMAIL_ADDRESS][PERSON_NAME],
phone [PHONE_NUMBER]. Architect: [PERSON_NAME], cell [PHONE_NUMBER].
```

**The SSN survived verbatim.** Names and phones were caught; the email was mangled into three overlapping tokens.

**Where.** `packages/permit_pilot_core/permit_pilot_core/security/pii.py`, Documents tab of any case with a packet.

**Root cause.** Production takes the Cloud DLP path *instead of* the regex path, not in addition to it:

```66:72:packages/permit_pilot_core/permit_pilot_core/security/pii.py
    project = os.environ.get("GOOGLE_CLOUD_PROJECT")
    if project and os.environ.get("K_SERVICE"):
        return _redact_dlp(text, project)
    redacted, findings = _redact_regex(text)
```

`_DLP_INFO_TYPES` does include `US_SOCIAL_SECURITY_NUMBER`, but `inspect_config` sets no `min_likelihood`, and DLP down-ranks well-known invalid/test SSN patterns. The local regex path at `pii.py:7` would have caught it (`\b\d{3}-\d{2}-\d{4}\b`), so the **production path is strictly weaker than the dev path** on the single most sensitive field.

**Why it matters.** This is the worst finding in the audit on both axes. As product: the placeholder text on that very form promises *"SSN, email, and phone will be redacted automatically"* — the feature visibly fails at the one thing it advertises. As a demo: if anyone types a plausible SSN during judging, the failure appears on screen in the "Fortified Enterprise" track. As production risk: unredacted SSNs written to Firestore is a reportable data-handling failure, and because the original text is never stored there is no recovery path — the mangled `[PERSON_NAME][EMAIL_ADDRESS][PERSON_NAME]` email is now unrecoverable data loss.

**Ideal behavior.** Deterministic patterns (SSN, email, phone) are always removed by regex; DLP runs on top for names and fuzzy types. Overlapping replacements do not corrupt adjacent text. The clerk sees a human-readable summary of what was removed and can review before committing.

**Fix.**
1. Run `_redact_regex` **first, always**, then pass the result to DLP. Belt and suspenders.
2. Set `"min_likelihood": "POSSIBLE"` and add `US_SOCIAL_SECURITY_NUMBER` to a custom regex ruleset in `inspect_config`.
3. Wrap `_redact_dlp` in try/except — currently a DLP outage is an unhandled 500 on intake (see GAP-11).
4. Add a redaction-preview step in the intake modal before the case is created.

**Perspective:** E, C, P.

#### GAP-05 · Case files take 12–22 seconds to open; approving took over a minute

**What is wrong.** Measured warm latency against the deployed service:

| Endpoint | Time |
|---|---|
| `GET /api/tasks?status=all` | 0.36s |
| `GET /api/cases` | 0.43s |
| **`GET /api/cases/{id}/bundle`** | **21.7s** |
| `GET /api/cases/{id}/bundle` (repeat) | **12.6s** |
| Cold start (first request) | ~10s |
| **Approve, click → UI settled** | **~60s** |

**Where.** `/cases/:id` — every case page load, every tab switch that triggers a reload, and after *every* mutating action (`runAction` always calls `load(true)`).

**Root cause.** The bundle endpoint makes uncached live Socrata calls on every single request:

```87:88:services/api/permit_pilot_api/routes/cases.py
    related_raw = await engine.related_permits(bbl=case.bbl, bin_=case.bin)
    parcel_raw = await engine.parcel_context(bbl=case.bbl)
```

`related_permits` issues two Socrata queries (by BBL, then by BIN) and dedupes; `parcel_context` a third. Nothing is cached — there is no cache layer anywhere in the engine or the Socrata client. Deployment settings compound it: `--cpu-throttling`, `--no-cpu-boost`, `--max-instances 1`, `--min-instances 0` (`scripts/deploy.sh:53-58`).

The 60s approve is the sum of `POST /decision` + `listTasks` + a **full bundle refetch**, serialized in `decide()` (`CasePage.tsx:169-181`).

**Why it matters.** 12–22s to open a case file is not usable by a clerk who processes a queue, and it is a live-demo killer: the presenter clicks a task and then talks over twenty seconds of skeleton loader. The approve path is worse because the user has already committed — they watch "Saving…" for a minute with no idea whether the decision landed. Two of these results are in the same order of magnitude as the 120s Cloud Run request timeout, so under Socrata latency spikes this becomes a 504.

**Ideal behavior.** Case file interactive in under a second. Live NYC data loads progressively into the sections that need it.

**Fix.**
1. **Split the bundle.** Return case/distribution/claims/audit/workflow/trace (all Firestore, fast) immediately; move `related_permits` and `parcel` to a separate `GET /cases/{id}/context` that the Summary tab fetches lazily with its own skeleton. This alone should take the case page under 1s.
2. **Cache Socrata responses** — persist `related_permits`/`parcel` to Firestore with a TTL and serve stale-while-revalidate.
3. **Stop refetching the bundle after every action.** Have mutating endpoints return the changed slice and patch state locally.
4. Reconsider `--max-instances 1` and `--cpu-throttling` for the judging window; add `--min-instances 1` to remove the 10s cold start.

**Perspective:** E, C, P.

#### GAP-06 · The Critic agent can never fail — the cite-or-reject guardrail is structurally inert

**What is wrong.** The Critic's only failure condition is a `FAIL` review that carries no citations. But **every** `FAIL` path in the engine hardcodes a citation, so the condition is unreachable. The Critic returns `PASS` on 100% of inputs.

**Where.** `packages/permit_pilot_core/permit_pilot_core/distribution/engine.py`.

```366:369:packages/permit_pilot_core/permit_pilot_core/distribution/engine.py
    async def review_critic(self, *, reviews: list[DepartmentReview]) -> DepartmentReview:
        failures = [r for r in reviews if r.status == ReviewStatus.FAIL]
        uncited_failures = [r for r in failures if not r.citations]
        if uncited_failures:
```

Every producer of a `FAIL` attaches a citation: `_BUILDING_FAIL_CITATION` (`engine.py:22`), `_FIRE_FAIL_CITATION` (`:27`), `_HOUSING_FAIL_CITATION` (`:32`), plus inline citations in the utilities (`:289`) and landmarks (`:332`) fail branches. Verified across four cases in the live system — Critic was `pass` every time, including on cases with two failing departments.

**Why it matters.** This is the project's headline agentic-safety feature, the thing that makes it a "Fortified Enterprise Fleet" entry rather than a data dashboard. In the running product it is a constant. A judge who asks *"show me the Critic rejecting a review"* cannot be satisfied — there is no input that produces it. Related: the Critic's evidence row is labeled **"Evidence (NYC Open Data)"** in the drawer but its `dataset_id` is `policy/cite-or-reject` (`engine.py:382`), so the UI mislabels a policy assertion as open-data evidence.

**Ideal behavior.** The Critic validates something that can actually fail — that the cited code section exists and is relevant to the finding, that evidence values support the stated conclusion, that a `PASS` isn't masking missing data.

**Fix.** Give the Critic a real job. Cheapest credible version: validate citations against a small real ordinance index and fail on codes that don't resolve or don't match the finding type; additionally fail when a department returns `PASS` with zero evidence rows (currently possible and silently accepted). Then seed one demo case that genuinely trips it. Also relabel the Critic's evidence section to "Policy check" rather than "Evidence (NYC Open Data)."

**Perspective:** C primarily, E and P secondarily.

#### GAP-07 · The crash/resume durable-workflow demo cannot be performed at all

**What is wrong.** `POST /api/cases/{id}/workflow/interrupt` returns:

```
HTTP 409 {"detail":"No running workflow step to interrupt"}
```

**Where.** No UI affordance exists for interrupt anywhere in the app (`api.ts:260` defines `interruptWorkflow`; nothing calls it — verified by grep across `web/src`). The API refuses when called directly.

**Root cause.** `mark_interrupted` only acts on a step in `RUNNING` state (`runner.py:68`). But distribution runs synchronously to completion inside the intake request (`cases.py:126`, `intake.py`), so by the time any client can issue a second request, all seven steps are `completed`. There is no window in which a step is `RUNNING`. The "Resume workflow" button is also gated on `stalled` (`CasePage.tsx:139`), which can therefore never be true — I confirmed the button count is **0** after attempting an interrupt.

**Why it matters.** This is demo beat #4 in the README's own script ("simulate kill → resume"). It is the entire justification for the Firestore-checkpoint architecture and the closest thing the project has to a durable-execution story. It is unreachable through the UI *and* through the API. If a judge asks to see it, there is nothing to show. Two of the three seeded cases have **zero** workflow steps at all, so even the static workflow strip is absent there.

**Ideal behavior.** A visible "Simulate worker crash" control on the Distribution tab that interrupts mid-run, shows the interrupted department as stalled with a clear banner, and a "Resume workflow" button that picks up from the checkpoint — demonstrably skipping already-completed departments.

**Fix.**
1. Make distribution **asynchronous**: intake returns immediately with steps `pending`, and a background task (or the existing Cloud Workflows execution) advances them. This makes the existing `checking` status, the 4s polling loop in `CasePage.tsx:141-145`, and the `CHECKING` placeholder in `runner.py:133-137` all come alive — right now that machinery is dead code because the work completes server-side before the client ever sees it.
2. Add the **Simulate crash** and **Run on Cloud Workflows** buttons to the Distribution tab (see GAP-09).
3. Fix `seeds.py` to create workflow steps and trace spans so seeded cases aren't inconsistent with app-created ones.

**Perspective:** C primarily, E and P secondarily.

#### GAP-08 · The UI asserts a DOB NOW handoff that does not exist

**What is wrong.** The Claims tab states: *"Claims are recorded on the case and handed off to DOB NOW with a reference ID for the audit trail."* After creating a claim the UI displays *"DOB NOW handoff · DOB-NOW-2CB35E94-F4C518"* and the audit log records *"DOB NOW handoff ref DOB-NOW-2CB35E94-F4C518."*

#### GAP-09 · `POST /api/cases/{id}/workflow/resume` is unauthenticated on a public service

**What is wrong.** The endpoint requires no credentials, returns case data, and mutates state.

```
$ curl -X POST .../api/cases/6b3e87ca-.../workflow/resume     # no token
200 {"step":null,"steps":[{"name":"distribution","department":"zoning",
     "status":"completed","detail":"PLUTO confirms zoning district R5B.", ...}]}

$ curl -X POST .../api/cases/does-not-exist/workflow/resume
404 {"detail":"Case not found"}
```

Every other endpoint correctly returns 401 (verified: `/api/cases`, `/api/tasks`, `/api/agents`, `/api/config/conditions`, `/api/cases/{id}/bundle`, and even `/workflow/interrupt`).

**Where.** `services/api/permit_pilot_api/routes/workflow.py:24-25` — the route omits the `get_current_user` dependency that its sibling routes carry. Deployed with `--allow-unauthenticated` (`deploy.sh:49`).

**Why it matters.** Four distinct problems: (1) unauthenticated read of workflow state including department findings and zoning data; (2) unauthenticated **write** — advances the workflow and appends audit events, corrupting the compliance trail; (3) case-ID enumeration oracle via the 404/200 split; (4) each call triggers live Socrata queries and Firestore writes on a `--max-instances 1` service, making it a trivial cost/availability amplifier. This is in the "Fortified Enterprise" track, where a judge poking at auth is a realistic scenario.

**Root cause of the design.** The route is intended for the Cloud Workflows OIDC caller (`infra/workflows/distribution.yaml:21-22` sends an OIDC token) but FastAPI never validates it, and Cloud Run IAM is disabled by `--allow-unauthenticated`.

**Ideal behavior.** Authenticated as either a clerk JWT or a verified Google-signed OIDC token from the workflow service account.

**Fix.** Add a dependency that accepts *either* a valid clerk JWT *or* a Google OIDC ID token verified against the workflow service account (`google.oauth2.id_token.verify_oauth2_token` with the expected audience). Reject everything else.

**Perspective:** P primarily; C if probed.

#### GAP-10 · The signed-agent gateway demo is unreachable: no UI, and the only account gets 403

**What is wrong.** The Agent registry drawer is a **read-only list**. Four cards, all badged "Signed," with fingerprints. There is no invoke button, no rogue-agent test, no action of any kind. And calling the endpoint directly fails for every signature variant:

```
valid building_agent fingerprint  → 403 {"detail":"Admin access required"}
rogue signature                   → 403 {"detail":"Admin access required"}
no signature                      → 403 {"detail":"Admin access required"}
```

**Where.** `AgentCatalog.tsx` renders no actions. `api.ts:263` defines `invokeAgent`; nothing calls it. `routes/agents.py:22` guards the route with `get_current_admin`, but the deployment hardcodes `CLERK_BOOTSTRAP_ROLE=clerk` (`deploy.sh:23`, `59`), and there is no admin account and no UI to create one.

**Why it matters.** README demo beat #2 is *"Agent Catalog — signed pass, rogue blocked."* It cannot be performed. The 403 you get is the *authorization* rejection, not the gateway rejection — so you cannot even demonstrate the gateway logic by hand. Two further problems if it were reachable: the "signature" is a plain string comparison against `sha256("permit-pilot:{name}")[:16]` (`security/agent_gateway.py:12-21`), not a cryptographic signature — describing it as signed A2A overstates it; and a successful invoke returns static JSON without running any agent (`agents.py:40`). The entire ADK orchestrator service (`services/orchestrator/`) is deployed but never called from the API.

**Ideal behavior.** A clerk can see the registry; an admin can run a live gateway test showing a signed agent admitted and a tampered agent blocked, with the rejection landing in the case audit trail.

**Fix.** Ordered by cost:
1. Add **"Test gateway"** and **"Send tampered request"** buttons to each agent card, wired to `api.invokeAgent`, showing the pass/block result inline and linking to the resulting audit event.
2. Relax the route from `get_current_admin` to `get_current_user`, or provision an admin account. Admin-only with no admin account is equivalent to disabled.
3. Rename to what it is: "fingerprint allowlist," not "signed A2A." Or implement real HMAC over the request body with a shared secret — that is a small change and makes the claim true.
4. Make a successful invoke actually call the ADK orchestrator, so the deployed second service earns its place in the architecture diagram.

**Perspective:** C primarily, P secondarily.

#### GAP-11 · Failure states have no recovery path, and raw technical errors reach the clerk

**What is wrong.** I injected failures on each critical endpoint. Results:

| Injected | What the clerk sees |
|---|---|
| `GET /bundle` → 500 | **Entire page replaced by one line of small red text.** No heading, no retry, no context. Retry affordances found: **none**. |
| `POST /orchestrate` → 502 | `"Vertex model unavailable"` — shown twice (inline banner + toast) |
| `POST /decision` → 500 | `"Firestore write failed"` — twice, plus dialog stays open |
| `POST /refresh` → network abort | `"Failed to fetch"` — twice |

Three separate problems:

**(a) No recovery from bundle failure.** `CasePage.tsx:187-189` renders `<p className="text-red-700">{error ?? "Case not found"}</p>` and nothing else. Since `/bundle` makes live Socrata calls on every load (GAP-05), a transient upstream failure is a *likely* state, not hypothetical — and the clerk's only option is to guess that reloading might help. Worse, a genuine 404 renders as bare "Case not found" (screenshot `46-bogus-case.png`), which is the same treatment. Contrast this with `NotFoundPage`, which is properly designed with a heading and two navigation links — the app has a good error page and doesn't use it.

**(b) Raw error strings.** `errorMessage` is a pass-through (`lib/errors.ts:22-26`), so backend internals (`"Firestore write failed"`) and browser internals (`"Failed to fetch"`) go straight to a permit clerk. Neither tells them whether to retry, wait, or escalate.

**(c) Every error is surfaced twice** — `runAction` sets inline state *and* pushes a toast (`CasePage.tsx:154-158`). On the decision failure the inline banner also renders *behind* the native modal, so it is invisible and inert while simultaneously shifting the page layout.

**Why it matters.** This is where a polished demo and a usable product diverge. Everything works on the happy path; the moment Socrata is slow, the case file becomes an unrecoverable dead end.

**Ideal behavior.** Failures render an in-context error card with the case header intact, a **Try again** button, and clerk-legible language. One surface per error.

**Fix.**
1. Keep the case shell rendered on bundle failure; put the error in the content area with a **Try again** button calling `load()`. Distinguish 404 (offer Back to tasks / Permit search, reusing `NotFoundPage`'s design) from 5xx (offer retry).
2. Add a message map in `errors.ts`: network/abort → "Can't reach Permit Pilot. Check your connection and try again."; 5xx → "Permit Pilot couldn't complete that. Try again — nothing was saved."; 502/503 on orchestrate → "The briefing model is unavailable right now. Department reviews are unaffected."
3. Pick one surface: inline for anything with a retry, toast for transient confirmations. Never both.
4. Wrap `_redact_dlp` in try/except with regex fallback — a DLP outage is currently an unhandled 500 that fails the whole intake (`pii.py:32-59`).

**Perspective:** E, P.

#### GAP-12 · Actions that change data give no confirmation; there is no data-freshness indicator

**What is wrong.** Several state-changing actions complete with zero positive feedback:

- **Refresh from NYC Open Data** — `runAction("refresh", …)` passes no `successMessage` (`CasePage.tsx:390`), so nothing is shown. Combined with GAP-03 (it does nothing) and the absence of a timestamp, the clerk has no way to know anything happened.
- **Resume workflow** — same, no `successMessage` (`CasePage.tsx:367`).

**Why it matters.** The user's own framing: *"anything that would make an employee question whether the system actually completed an action."* This is the cleanest instance of it in the product. **Ideal behavior.** Every mutating action produces a confirmation. The distribution table carries a visible "Data as of <timestamp>" with per-row staleness.

**Fix.** Add `successMessage` to the refresh and resume actions. Add an `Updated` column to the distribution table plus a header-level "Data as of …" derived from `max(updated_at)`, with a stale warning past a threshold. Make the decision-success toast sticky until dismissed, or replace it with the (currently dead) inline "Decision saved" banner.

#### GAP-15 · The clerk note is a single-line input, and condition chips corrupt it

**What is wrong.** The clerk note is the legal record of a permit decision. It is a single-line `<input>` (`CasePage.tsx:718-724`) with no minimum length, no character counter, and no draft persistence.

Two concrete failures:

1. **Condition chips produce corrupted text.** `appendCondition` joins with a newline (`CasePage.tsx:165`), but a single-line `<input>` strips newlines. Observed: with `"x"` in the field, clicking `BC 3301` yielded `"xBC 3301: Submit updated site safety plan per BC Chapter 33 before work begins."` — no separator. Clicking multiple chips concatenates them into one unreadable run-on.
2. **A one-character note passes validation.** `"x"` opened the approve confirmation and would have been written to the audit trail. This is not theoretical: the pre-existing approved case `43-30 PARSONS BOULEVARD` has an audit entry reading `Approve / j` — a real permit approval, with two failing departments and 52 active DOB violations overridden, justified by the letter "j".

Also: the note is lost if the tab is closed (no draft persistence), and six unlabeled code chips (`BC 3301`, `LPC Rule 2-01`, `DEP Rules`, `BC 28-104`, `BC 28-105`, `AC 28-105.12`) sit above the field with no heading and no hint that clicking them inserts text — undiscoverable, and they occupy a full row of the sticky footer on every tab.

**Ideal behavior.** A multi-line textarea with a meaningful minimum for override decisions, autosaved drafts, and clearly-labeled condition chips that insert as readable separate lines.

**Fix.** Swap the `<input>` for a `<textarea>`. Require a longer note (e.g. 20+ chars) when `override` is true, with a message explaining why. Persist drafts to `sessionStorage` per case (the pattern already exists in `briefingCache.ts`). Give the chips a label — "Insert standard condition:" — and consider a dropdown rather than six always-visible buttons.

**Perspective:** E, P — and C, since "Approve / j" is discoverable in the audit tab during judging.

#### GAP-16 · Terminal cases remain mutable; approval can race a concurrent refresh

**What is wrong.** Two related integrity gaps.

**(a) Approved cases can still be modified.** After approving, the decision footer correctly disappears, but **Refresh from NYC Open Data** and **Generate clerk briefing** both remain enabled. A clerk can alter the distribution data underlying a closed decision, after the fact. `TERMINAL` gating (`CasePage.tsx:18`) is applied to `canDecide` but not to these actions.

**(b) Approve is not disabled during a refresh.** Measured mid-refresh: `approve disabled = false`. The `busy` key is per-action (`CasePage.tsx:42`), so a distribution refresh does not block the decision buttons. A clerk can approve while department reviews are being re-fetched, committing a decision against data that is actively changing. The `checking` guard (`CasePage.tsx:729`) only covers reviews already in `checking` state, not an in-flight refresh.

Related: the mid-flight loading state on refresh is effectively invisible — the button label never rendered as "Refreshing…" during my test because the request returned in under 400ms (GAP-03).

**Why it matters.** For a system whose value proposition is a defensible audit trail, "the record can change after the decision" and "the decision can be made against changing data" are direct contradictions of the premise.

**Ideal behavior.** Terminal cases are read-only except for an explicit, audited reopen. Any in-flight data mutation blocks decision actions.

**Fix.** Gate refresh and briefing on `canDecide` (or add an explicit audited **Reopen case** action). Add a `mutating` boolean derived from `busy` and disable the decision buttons whenever it is set, with a tooltip explaining why.

**Perspective:** E, P, C.

## 4. Competition assessment

**The differentiation is real but it is not the differentiation the project claims.** What is actually distinctive is the depth of the NYC Open Data integration: seven departments against eleven real Socrata datasets, keyed on BBL/BIN, with per-finding evidence rows citing dataset IDs. Most agent hackathon projects wrap a single LLM in a chat box; this one does genuine domain integration against a real municipal data estate, and the domain modeling (BBL borough digits, DOB violation categories, HPD Class A, DEP ECB, LPC historic districts) reflects actual research. That is hard to fake and hard to match.

**But all three claimed differentiators are inert in the running product.** The Critic cannot fail (GAP-06). The crash/resume workflow cannot be triggered (GAP-07). The agent gateway has no UI and 403s for the only account (GAP-10). The README's demo script has seven beats; **three of them are impossible to perform**. A judge following that script hits a wall at beat 2.

**The core problem is not immediately obvious from the UI.** Landing on an empty "My Tasks" (GAP-01), a first-time viewer has no idea what problem this solves. There is no onboarding, no sample case call-out, no explanation of what "distribution" means in a permit context — a term of art that is central to the product and never defined anywhere in the interface. The README explains the problem well; the product does not.

**What is impressive vs. ordinary.** Impressive: the department drawers with real dataset-cited evidence; the Vertex briefing correctly synthesizing across seven departments; the trace spans with real per-department durations. Ordinary: the task table, the search page, the audit list. Weak/superficial: the agent registry (a static list with no action), the "Trace replay" (a flat list), the DOB NOW handoff (a fabricated string).

**Specific live-demo risks, in order of likelihood:**
1. The landing page is empty. Unavoidable, first thing on screen.
2. A 12–22 second wait to open a case, and ~60 seconds to approve — dead air at the two most important moments.
3. The confirmation dialog appears in the top-left corner during the approve beat.
4. Cold start adds ~10s if the service has scaled to zero before the demo.
5. `--max-instances 1` with CPU throttling: if judges browse concurrently while the presenter demos, everyone slows down.
6. If anyone types an SSN, it appears unredacted on screen.
7. Any Socrata slowness turns the case file into an unrecoverable error line.

**What a top-tier competitor would have that this does not:** a working end-to-end loop that closes (task → review → decide → next task); at least one agent decision that visibly changes based on evidence rather than executing a fixed rule; a guardrail that observably rejects something; sub-second interaction; and a demo that survives being driven by someone other than the author.

**The strongest available repositioning.** Stop selling the multi-agent framing, which the implementation does not support — the departments are deterministic rule engines, not agents, and describing them as agents invites a question the code answers badly. Sell what is actually true and actually rare: *"Seven NYC departments, eleven live open-data sources, one clerk decision, one defensible audit trail."* Then make the Critic genuinely fail on one seeded case and put the crash/resume button on screen. That is a credible top-tier story built on work already done.

## 7. Honest bottom line

The engineering underneath Permit Pilot is better than the experience of using it. Real GCP services are wired for real — Firestore, Vertex, DLP, Cloud Trace, Cloud Workflows are all genuinely called, not stubbed — and the NYC data integration is the most credible thing in the project. The design system is coherent, the state machine works, and the audit trail is real. Someone with judgment built this: the "internal target, not a statutory SLA" label and the "this does not notify the applicant" disclaimer are the marks of a builder who understood the domain well enough to know where the boundaries were.

What holds it back is that **the demonstration layer never got the same rigor as the plumbing**. The three features chosen as the headline story are the three that don't work in the product. The landing page is empty. The most important dialog is in the wrong corner of the screen. The refresh button lies. Opening a case takes twenty seconds. Each of these is small, and several are one-line fixes — but they are all in the first ninety seconds, so they define the entire impression. Right now the product reads as a polished shell with hollow spots exactly where a judge will press.

The gap between this and a top-tier submission is not more features. It is roughly one focused day: fix the six items in the "before any demo" list, then make the Critic fail once and put the crash/resume button on screen. The differentiated work is already done and paid for — it is just not reachable from the UI.
